# 写作规范

每章默认使用一个 notebook 作为完整阅读入口。

## 风格要求

默认风格：**结论先行，平铺直叙，高信息密度**。

要求：

- 先给判断，再解释原因。
- 少写铺垫，少写情绪，少写“为什么重要”的长段落。
- 不写废话文学，不写口号式表达。
- 能用表格就不用长段落。
- 能用清单就不用散文。
- 能用例子说明就不要抽象绕圈。
- 复杂概念可以补充说明，但必须先给结论。
- 每段只承担一个信息点。
- 文章要像工程笔记，不像营销稿。
- 优先使用“需要具备以下技能”“包含以下模块”“流程如下”这类直接表达。
- 开头必须在三秒内说明本章主题、读者能获得什么和最重要的结论。
- 使用 `1`、`1.1`、`1.1.1` 形式的树形标题组织长文。
- 原理章节先讲背景、原因、术语、参与者、数据流和时序，再进入代码。
- 代码用于观察和验证原理，不把读懂复杂代码作为理解概念的前提。
- 优先用流程图、时序图、数据结构示意和逐步输出降低理解成本。

避免：

- “随着 AI 的发展……”
- “在当今时代……”
- “我们不难发现……”
- “这就引出了一个问题……”
- “想象一下……”
- “不是 X，而是 Y”
- “核心问题不是 X，而是 Y”
- 连续使用“能不能……”
- 连续使用设问句
- 没有新增信息的过渡句
- 一句话解释后紧跟数百行代码
- 为了统一案例强行引入尚未铺垫的产品对象

Notebook 结构模板见 [notebook-template.md](notebook-template.md)。

## 代码结构

每章目录建议包含：

```text
notebooks/
examples/
tests/
notes.md
```

其中：

- `notebooks/` 放学习主线，是每章唯一必需入口。
- `examples/` 放脚本化示例，作为 notebook 之后的工程化版本。
- `tests/` 放必要的测试或验证脚本。
- `notes.md` 放调研笔记、草稿、参考链接和暂时不进正文的内容。

## 代码要求

- 每章优先提供 `.ipynb`，代码和解释放在同一个阅读路径里。
- notebook 按“概念 -> 代码 -> 输出 -> 断言 -> 边界”组织。
- 脚本示例只在需要复用、测试或工程化时提供。
- 每个示例都写清楚依赖、环境变量和运行命令。
- API key 使用 `.env.example` 描述，不提交真实密钥。
- 每个示例都尽量输出中间过程，方便读者看到模型如何选工具、如何失败、如何修正。
- 每个代码单元只观察一个关键步骤。
- 代码前说明输入、当前参与者、即将发生的动作和预期输出。
- 代码后解释输出证明了什么。
- 完整工程封装放在读者理解协议和数据流之后。

## 课程案例

- 第 1 至 12 章以学习单项技术为主。
- 每章选择最适合当前概念的案例，不要求连续使用同一个业务场景。
- 案例优先满足直观、短小、输入输出明显和便于制造边界条件。
- 可以在章末简要说明当前技术与最终项目的关系。
- 第 13 章集中设计和实现产研协作助手，复用前面已经讲透的技术。
- 不为最终项目提前引入会增加当前章节理解成本的业务对象、状态或控制协议。

## 写作口径

- 少用“玄学 prompt”，多讲输入、约束、格式、反馈和评测。
- 少写框架崇拜，多写框架帮我们解决了什么工程问题。
- 少写“Agent 无所不能”，多写权限、成本、失败率和人工兜底。
- 复杂概念先给工程结论，再补必要术语和例子。
